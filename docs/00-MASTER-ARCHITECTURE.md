## 2. Multi-Tenancy Strategy

**Shared database, shared schema.** Every tenant-scoped table carries an `organizationId` (uuid, FK to `Organization.id`, indexed, `NOT NULL` for tenant data).

Rules for every module doc / every new table:

- All Prisma models representing tenant data MUST include `organizationId String` with a relation to `Organization`, and an `@@index([organizationId])`.
- All NestJS services MUST filter every query by the authenticated user's `organizationId` (from the JWT payload) — never trust a client-supplied `organizationId`.
- Global tables that are NOT tenant-scoped (e.g. system-level lookup tables, the `Organization` table itself, platform-admin tables) must be explicitly marked as such in `01-DATABASE-SCHEMA.md`.
- Add a NestJS guard/interceptor pattern (if not already present) that injects `organizationId` from the authenticated request into repository/service calls, so it's structurally hard to forget the filter. Check `backend/src/` for whether this already exists before building a new one.
- Platform Super Admin (see Module 19, SaaS Administration) is the one role allowed to query across organizations, and only through explicitly separate admin endpoints — never by relaxing the tenant filter on normal endpoints.

#### Module 14 (Utilities) — found while designing it, 2026-10-06
99. ❌ **This row said "Absent — confirmed by audit" and was half wrong, in the direction that hides the work.** Four utility-adjacent tables exist (`UnitMeterNumber`, `UnitServiceCharge`, `PropertyStandingCharge`, `Unit.*Acno`) and all four are **empty**. The audit read "no utilities tables" from table names and stopped; it did not notice that `UnitMeterNumber` was the meter registry already half-built. **Zero rows is not the same as absent, and the difference decides the work**: a populated half-table must be reconciled, whereas an empty one can be reshaped for free. This is the audit's blind spot generalised — it greps for names, not for *what a table can answer*. Several "Absent" rows in the table above deserve the same re-check on that basis.
100. ❌ **The module doc's target schema cannot meet its own acceptance criterion, and the gap is a missing table rather than a wrong column.** The criterion is "reading delta × rate" and the target models include no rate. `UtilityRate` is therefore new, and it is the single table that makes the criterion reachable. **The check to apply to any spec with a formula in it: name every symbol the formula needs, then find the table that holds it.** A doc that specifies a computation without specifying its inputs has specified nothing testable.
101. ❌ **The pre-existing `UnitMeterNumber` was a meter registry that could not answer a single question about a meter.** No `type` (so water and electricity were indistinguishable), no `propertyId`, no readings, no rate, and a `readingSetup` free-text string carrying the only useful idea in it. It is why Module 14 renames and reshapes it into `UtilityMeter` rather than creating a fifth utility table beside it — **the same "two tables for one thing" defect as `Supplier` (issue list, Module 10) and `landlordId`/`tenantId`.** Note the general rule this keeps confirming: a table with zero rows is not dead code to be preserved out of caution, it is an unfinished sentence.
102. ⚠️ **A utility invoice that sets `billingPeriod` would silently stop the rent run for that month.** `invoices` has `@@unique([rentalAgreementId, billingPeriod])` because a lease gets one rent bill per month, and `recurring-billing.service.ts:45` documents that a second attempt "fails that constraint and is reported as *skipped*, which is the correct outcome". A consumption invoice is also *per lease, per month* — so it collides by construction, and creating it would make the rent run skip, leaving the resident billed for water and **not** for rent. The fix is structural, not defensive: utility bills leave `billingPeriod` **null**, are classified `transactionClass = 'UTILITY'`, and `UtilityCharge` owns the period. **This is the general hazard of reusing an existing table for a new document type: the table's uniqueness rules encode the *old* document's invariants and will refuse or, worse, silently displace the new one.** Check what a table's constraints *mean* before writing through them.
103. ⚠️ **The exactly-once billing constraint is null-unsafe, which is exactly where it matters most.** `UtilityCharge @@unique([meterId, unitId, billingPeriod])` is what stops a resident getting two bills for one month's water — but bulk meters have **no `unitId` by definition** (`scope = BULK`, the riser meter the estate re-sells), and PostgreSQL treats NULLs as distinct in a unique index. So the constraint silently does not apply to the case that most needs it. Needs a partial unique index on `COALESCE(unitId, '')`. **General rule: a nullable column inside a `@@unique` is a constraint with a hole in it, and the hole sits on whichever case made the column nullable.**
104. ⚠️ **Naive consumption arithmetic is catastrophically wrong on a rolled-over meter.** A 5-digit register reading 99998 then 00003 consumed **5** units; the subtraction returns −99995 and, metered onto an invoice, becomes a five-figure credit. `UtilityMeter.digits`/`digitWrapAt` handle it and are **null by default**, so an ordinary meter cannot be affected by the logic unless someone deliberately turns it on. **Opt-in special-casing beats always-on: a rollover fix applied unconditionally would be a permanent risk to pay for an edge case.**
105. Open: **`UnitServiceCharge.totalCost` is a stored derivation, and `costPerArea` beside it is the input.** Every module this codebase has built since Module 8 reaches for "derived, never stored", and this column predates all of them. Deliberately **not** touched as part of Module 14 — it is a fixed *service* charge rather than a metered one, so it is arguably out of scope, and silently refactoring pre-existing debt is how a module stops being reviewable. `PropertyStandingCharge` is its true relative and has a worse problem: **no validity window**, so it cannot express "this charge applied until March", and `chargeUtility`/`chargeMode` are free text.
106. Open: **`Unit.electricityAcno` / `waterAcno` / `electricityMeethno` / `waterMeethno` are now redundant** with `UtilityMeter.meterNumber`, and they cover exactly four utility types — a fifth needs a migration. All four columns are 0-populated, so removal is cheap, but it is not this module's job.
107. ✅ **Closed by turning a question into data.** Water keeps arriving on a bulk meter whether or not anybody is home to use it, and every answer to "who carries a vacant unit's water" is a trade-off — absorb it, re-rate it across the occupied units, or don't bill it — so which one is right belongs to the landlord rather than to a module. `Organization.vacancyPolicy` (`RECORD_ONLY` / `SKIP` / `REDISTRIBUTE`) stores the decision, on the organization because an estate group wants it uniform. **Null means `RECORD_ONLY`, and that is chosen rather than neutral**: it makes a real cost visible without inventing a payer, which is the failure the other two options accept on purpose. `SKIP` voids the charge with its reason kept; `REDISTRIBUTE` is **refused rather than performed**, because moving one unit's share onto its neighbours changes what *other* residents owe and a billing run is not the place to decide that. **The generalisation: an undecided policy question that the code keeps re-asking is a missing column, not a missing feature — and the honest default is the branch that refuses to invent an answer.**
108. ✅ **A `CHECK` constraint that did not enforce what it said, because of three-valued logic.** Module 14's `utility_meters_rollover_consistent` reads as "a meter that declares its digit count declares a wrap point of exactly `10 ** digits`" — and **accepted `digits = 5` with `digitWrapAt = NULL`**. The predicate is `(false) OR (true AND NULL = 100000)`, which is `NULL`, and **a CHECK constraint rejects only `FALSE`**. The constraint whose entire purpose is to make rollover arithmetic safe was the one that could be silently absent, and a meter in that state makes consumption arithmetic divide by nothing. Found by a SQL probe, not by reading the SQL. All three nullable-column CHECKs rewritten as `CASE ... ELSE false`. **The general rule: a CHECK over nullable columns written as a bare `OR` chain is not a constraint, it is a suggestion. Write `CASE ... ELSE false`, and probe each one with an insert you expect to fail.**
109. ✅ **A period window computed in the wrong time frame — issue 97 arriving through the database.** Module 14 priced a period as `[localMidnight, nextLocalMidnight)` while readings are stored as UTC instants (`TIMESTAMP(3) WITHOUT TIME ZONE`). On this UTC+3 server a reading taken **on** the 1st sorted *after* the period it opens, so a month could not be priced at all, and the API told an operator to go and record an opening reading they had already recorded. Fixed by `utcPeriodWindow` for queries, with **no local-time sibling** — a second function whose only job is to be wrong somewhere is speculative surface. Note the related surprise: **both** bounds are inclusive, which breaks the `[from, to)` convention the rest of this codebase uses, and is correct here because one reading closes one period and opens the next while the deltas stay adjacent. **A time-window rule has to be re-derived per domain; "we use half-open intervals" is not a transferable fact.**
110. ✅ **Two guards written from the wrong direction, both caught before shipping.** A rollover check of `if (to < wrapAt || from >= wrapAt) → refuse` refuses 99998 → 00003 — the exact case it exists to handle. And a "the register went round twice" refusal with a good error message turned out **provably unreachable**, since `to <= from - 1` forces consumption `<= wrapAt - 1`. **The checks to run on any guard that refuses: (a) does it reject the case it was written for, and (b) can it ever actually fire?** An unreachable branch with an explanatory message is worse than no branch, because it reads as coverage.
111. ✅ **An enum value the code silently did not implement.** `ApportionmentMethod.OCCUPANCY` shipped working as a *label* and not as behaviour: `apportion()` took an `occupiedDays` figure, but the service supplied only the month's length and no per-unit occupancy, so the method quietly degraded to `EQUAL` and the register named it `Split by days occupied`. **Every unit was charged a full month of a shared meter regardless of when they moved in, under a split described as proration.** Fixed with a pure `occupiedDaysInPeriod` (10 tests) and one batched tenancy query, which also removed an N+1 the old per-unit `activeLeaseFor` loop would have made worse as towers grew. Two rules: a tenancy covers `startDate` **through** `endDate` inclusive while the billing window is `[from, to)` — mixing the two conventions drops a day at every boundary — and overlapping tenancies are **unioned, not summed**, so a renewal recorded twice cannot report 62 days in a 31-day month. **The generalisation: an enum value that no test distinguishes from its neighbour is not implemented. A method that silently falls back to another method is worse than one that is missing, because the label on the register then lies.**
112. ✅ **A payload that contradicted its own declared type.** `GET /utilities/meters/:id` built its reading ledger by mapping `presentReading` directly, so the response carried only the four arithmetic fields — no `id`, `source`, `note` or provenance — while the frontend's `MeterReadingRow` declared all of them. The type was asserting a shape the API was not sending, and the meter's own screen could not key or correct a reading. Both paths now go through one shaper. **A hand-written `interface` over an inferred server response is a claim, not a check; the two shapes have to be built in one place or they drift, and the drift shows up as a UI that cannot do something the type said it could.**
113. X **A country-flavoured design decision, justified by that country's practice, in a codebase that exists to be the opposite.** Module 14 hardcoded utility charges onto their own separate invoice and defended it as "correct, but not what a Kenyan estate usually does" - the objection being that residents expect utilities bundled into the monthly bill. Both halves were wrong. It treated one market's norm as the standard in a schema whose stated architecture is that *jurisdiction is configuration* (`taxCountryCode` + `TaxRule` because "tax is configuration, not code", `payrollCountryCode`, ISO-4217 `currency`, `defaultLocale`, `timezone`). And it was wrong on the merits: across the markets this product targets a resident often holds the utility account themselves - the norm in the US and Canada - and an organization there still wants consumption recorded to reconcile the estate against what the utility company billed, while having **no standing to raise them an invoice**. Now `Organization.utilityBillingMode`: `SEPARATE_STATEMENT` (default) or `DIRECT_ACCOUNT`, which prices the period, marks the charge `RECONCILED` and raises nothing. `RECONCILED` is a **status** rather than a nullable `invoiceId` because "priced and reconciled" is a real end state and not the absence of one - leaving such charges `PENDING` would make every reconciliation report show finished work as outstanding. The third arrangement (bundling into the rent bill, or a consolidated service-charge statement) is **named in the enum's comment and deliberately unimplemented**: it collides with `billingPeriod` and would double-bill against `UnitServiceCharge`, which already puts fixed per-unit utility charges on the rent invoice. **The generalisation: when a design decision in a multi-jurisdiction product is defended by citing one country's practice, the reasoning is the bug even when the outcome is defensible - and a real market difference belongs in an org-level column, the same as tax and currency, not in a code comment explaining why the alternative was never considered.**

### 3.5 Recommended phased roadmap (supersedes the simple module-order table alone — read both)

**Phase 0 — Foundation (P0, do this first, largely = Module 0 Stabilization + hardening in Module 1 Core Platform):**

2. Fix navigation/route contracts; add detail/edit pages, row actions, and consistent empty/error/loading states as a cross-cutting pass (see `00-UX-CROSS-CUTTING-STANDARDS.md`).
3. Enforce tenant isolation + RBAC at controller/DTO level; fix wildcard CORS; move off JWT-in-localStorage.
4. Add transactional boundaries, idempotency where money moves, and make `AuditLog`/`logAction` actually get called on sensitive actions.
5. Fix docs/seed mismatch, add `.gitattributes`, clean the lockfile/CRLF noise, add real tests and CI.

**Phase 1 — Core revenue workflow (P0/P1):**
1. Onboarding/import flows for properties, units, tenants.
2. Real lease lifecycle: templates, e-signature, renewals, move-in/out inspections.
3. Recurring invoices, mobile money and payment gateway integrations (M-Pesa, Stripe, etc.) with reconciliation, payment allocation to invoices, receipts, local tax compliance transmission.

5. Live, API-driven dashboards and exportable reports.

**Phase 2 — Operational differentiation (P1/P2):**
1. Tenant, owner, and caretaker portals.
2. ~~Maintenance/work orders~~ (built in Module 9, 2026-10-04), inspections, document management.
3. Communications (SMS/email/WhatsApp), notifications, two-way messaging.
4. Mobile PWA / responsive optimization pass.
5. ~~Facility bookings, visitor log and access cards~~ (built in Module 13, 2026-10-05). Two halves of it are Phase 2/3 work rather than Phase 1 and are deliberately not done: **a resident booking their own facility from the portal** (the same gap as issue 86 — the tenant portal can see nothing from Module 13), and **reader/turnstile integration**, which is vendor-specific per estate. Also still open, and cheaper than either: **revoking a holder's access cards when they move out**, which is a change to the move-out flow rather than to this module (issue 94).

Sequenced here rather than in Phase 1 because it is the one Phase 1-shaped module whose *integration* is the hard part: it writes into Finance, so it must not go in before the recurring-billing invariant it would collide with (`@@unique([rentalAgreementId, billingPeriod])`, issue 102) is understood. Two halves are later-phase by design and deliberately not in the build: **smart/AMI meter ingestion** (vendor-specific per utility, which is why `MeterReadingSource.SMART` exists in the enum from day one but has no writer), and **a tenant-facing consumption view** — the visible gap in the benchmark, and a portal item alongside issue 86.

**Phase 3 — ERP maturity (P2/P3):**
1. Chart of accounts, full GL, bank reconciliation, accounts payable, budgets, fixed assets.
2. Automation/scheduler, webhooks, third-party integrations, open API.
3. Advanced analytics/forecasting, compliance (GDPR, ODPC, data retention policy).

**Phase 4 — Supply chain (P2, where procurement leaves off):**
1. ~~Purchase requests, RFQs and purchase orders~~ (built in Module 10, 2026-10-05) and ~~the inventory
   side it was waiting on: stock-in from goods receipts, reorder levels~~ (built in Module 11,
   2026-10-05). Still open: **supplier lead times feeding the order date** (issue 83 — the reorder
   suggestion knows *what* to order but not *when* it will arrive, because `Supplier` has no
   standing `leadTimeDays`), and the **remembered receipt-line → item pairing** that would take the
   manual step out of stock-in (issue 82).
2. Supplier-facing portal: a supplier sees their own invitations, submits their own quotation, and sees
   their orders and what is still outstanding (issue 80).
3. Returns and supplier credits out of a purchase order (issue 78), and contract management with
   renewal reminders (issue 72's remaining half).

Use this phase ordering to sequence work *within and across* the per-module docs in Section 4 — a module doc's own task checklist is still the operational detail, but Phase 0 items across multiple modules should be done before deep Phase 2/3 work on any single module.

## 6. General Engineering Conventions

- **Validation:** All NestJS DTOs use `class-validator` decorators; reject invalid input at the controller boundary.
- **Auth:** All non-public endpoints require the JWT guard; role-based access via a roles guard/decorator (check what exists in `backend/src/` already before adding a new pattern).
- **Dependency injection:** Nest reads a provider's constructor dependencies from `design:paramtypes`, which is erased by two ordinary-looking TypeScript habits. **Never** type an injected dependency as `import('./x.service').X` or `import type { X }` — it disappears from the metadata and the app fails at boot with "can't resolve dependencies of … (?, Object, Function)". **Never** give an injected dependency a default value (`http: HttpClientLike = fetch`) — Nest sees `Function`, tries to resolve a provider with that name, and boot fails. Both shapes were found in Module 17's notification providers and took the whole application down; use an explicit injection token (`@Optional() @Inject(TOKEN)`) for a test seam, and `forwardRef` on both sides for a genuine circular import.
- **Errors:** Consistent NestJS exception filters; don't leak stack traces in production responses.
- **Migrations:** All schema changes go through `prisma migrate dev` (or equivalent) — never hand-edit the DB, never use `prisma db push` for anything beyond local prototyping.
- **CORS:** Must be restricted to known frontend origin(s) in every environment except local dev — this is flagged as a Known Issue above; fix it, don't leave it open.
- **Frontend data fetching:** Use the existing Axios client pattern in `frontend/lib/api.ts`; remove dead/legacy API clients rather than leaving them alongside working ones (see `billingApi` issue).
- **Forms:** React Hook Form + Zod validation on every create/edit form; a form must not "log to console and pretend to succeed" (see rent-receipt bug) — always wire to a real mutation with loading/error states.
- **Currency:** All monetary fields support multi-currency (default to a configurable org-level currency); store amounts as integers (cents/lowest unit) or `Decimal` in Postgres — never `float`. Confirm which convention the existing schema already uses and stay consistent.
- **Naming:** Match existing Prisma model naming conventions already in `schema.prisma` (PascalCase models, camelCase fields) rather than introducing a new convention.
- **UI/UX standards:** Read `00-UX-CROSS-CUTTING-STANDARDS.md` before building or touching any frontend page — the audit found the same set of gaps (no detail/edit pages, no row actions, no bulk ops, no exports, inconsistent empty/error/loading states, weak accessibility/mobile support) repeated across nearly every existing page, and every new module should not repeat that pattern.
- **Audit logging:** `AuditLog` model and `logAction()` service already exist (`backend/src/modules/audit/audit.service.ts`) but are currently called nowhere. Every module that creates/updates/deletes tenant data, and especially every module touching money or auth, MUST call `logAction()` on those operations going forward — this is a standing requirement for all new work, not a one-time backlog item.
- **Don't duplicate existing "bloat" fields:** the schema already has some accounting/integration-oriented fields sitting unused (e.g. `acReceivable`, `incomeAccount`, `spotRate`, `Property.mpesaPropertyPayNumber`, `Invoice.signOnEfims`, `Receipt.bankingDate`, `exemptAllSms`). Before adding a new field for something that sounds similar, check whether one of these already covers it and wire logic to the existing field instead.
